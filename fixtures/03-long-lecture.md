# 前回の復習

## SQL の基本

前回は、テーブルからデータを取り出す `SELECT` 文を学びました。

```sql
SELECT name, price
FROM products
WHERE category = 'book'
ORDER BY price DESC
LIMIT 10;
```

この文は「本のカテゴリーの商品を、価格の高い順に10件取り出す」という意味です。

## 今日のテーマ

前回のクエリは、商品が100件なら一瞬で終わります。では、商品が1億件になったらどうでしょうか。

今日は次の3つを学びます：

1. データベースがデータを探す仕組み
2. インデックスで検索を速くする方法
3. 実行計画を読んで遅いクエリを直す方法

# データを探す仕組み

## 全件走査

インデックスがない場合、データベースは条件に合う行を探すために、テーブルの先頭から最後まですべての行を読みます。これを**全件走査**（フルテーブルスキャン）と呼びます。

全件走査にかかる時間は、テーブルの行数に比例します。行数が10倍になれば、検索時間もおよそ10倍になります。

### 本の索引で考える

分厚い専門書で「正規化」という言葉が出てくるページを探す場面を考えてみましょう。

索引がなければ、1ページ目から順にすべてのページを読むしかありません。索引があれば、五十音順に並んだ索引から「正規化」を探し、そこに書かれたページ番号を開くだけで済みます。

データベースのインデックスは、この本の索引と同じ役割を果たします。

### ディスクとメモリ

データベースのデータは、普段はディスクに保存されています。ディスクからの読み込みはメモリからの読み込みよりも桁違いに遅いため、検索の速さは「ディスクから何回読み込むか」でほぼ決まります。

データベースはデータを「ページ」と呼ばれる固定長の単位（多くの製品で 8KB や 16KB）で読み書きします。1行だけ必要でも、その行を含むページ全体を読み込みます。

## 検索にかかる時間の比較

1億行のテーブルから1行を探すとき、読み込むページ数は次のように変わります。

| 方法 | 読み込むページ数の目安 | 時間の目安 |
|---|---:|---:|
| 全件走査 | 約 1,000,000 | 数十秒 |
| B-tree インデックス | 4〜5 | 数ミリ秒 |

インデックスを使うと、読み込むページ数が20万分の1以下になります。

# インデックスの仕組み

## B-tree

多くのデータベースで標準的に使われるインデックスは **B-tree**（正確には B+tree）という木構造です。

![B-tree の構造](./assets/landscape-16x9.png "B-tree：根から葉までの深さが一定に保たれる")

B-tree には次の特徴があります：

- 根から葉までの深さがすべて同じ
- 1つのノードに数百個のキーが入る
- キーは常に順番に並んでいる
- 葉どうしがつながっていて、範囲を順にたどれる

1つのノードに数百個のキーが入るため、木の深さは非常に浅くなります。1億件のデータでも、深さは4〜5段で済みます。

## B-tree での検索の流れ

`id = 4,201` の行を探す場合を考えます。

### 1. 根から始める

根のノードには「1〜2,000 は左、2,001〜5,000 は中央、5,001以上は右」のような区切りのキーが並んでいます。4,201 は中央の子に進みます。

### 2. 中間のノードをたどる

中間のノードでも同じように、区切りのキーと比べて進む子を選びます。これを葉に着くまで繰り返します。

### 3. 葉で行の場所を得る

葉のノードには、キーと、そのキーを持つ行がテーブルのどこにあるかを示す情報が入っています。この情報を使ってテーブルのページを1つ読み、目的の行を取り出します。

### 4. 合計の読み込み

根・中間・葉で3〜4ページ、テーブルで1ページ。合計でも数ページを読むだけで済みます。全件走査の100万ページと比べると、その差は歴然です。

## 範囲検索

B-tree はキーが順番に並んでいるため、範囲を指定した検索も得意です。

```sql
SELECT * FROM orders
WHERE ordered_at BETWEEN '2026-10-01' AND '2026-10-07';
```

このクエリでは、まず `2026-10-01` の位置を木をたどって見つけ、そこから葉を右にたどりながら `2026-10-07` を超えるまで読み進めます。

## ハッシュインデックス

B-tree のほかに、**ハッシュインデックス**という種類もあります。キーからハッシュ値を計算し、その値で直接場所を求めます。

:::row
### 得意なこと
- 等号での検索（`=`）
- キーの長さに関係なく一定の速さ

### 苦手なこと
- 範囲検索（`<` `>` `BETWEEN`）
- 並べ替え（`ORDER BY`）
- 前方一致（`LIKE 'abc%'`）
:::

実際の業務では、範囲検索や並べ替えにも使える B-tree を選ぶことがほとんどです。

# インデックスの設計

ここからは、実際にインデックスを作るときの考え方を学びます。

## インデックスを作る

インデックスは `CREATE INDEX` 文で作ります。

```sql
CREATE INDEX idx_orders_customer
  ON orders (customer_id);
```

インデックスを作ったあとは、`WHERE customer_id = ...` を含むクエリが自動的にこのインデックスを使うようになります。クエリを書き換える必要はありません。

## 複合インデックス

複数の列を組み合わせたインデックスを**複合インデックス**と呼びます。

```sql
CREATE INDEX idx_orders_customer_date
  ON orders (customer_id, ordered_at);
```

### 列の順番が重要

複合インデックスは、電話帳の「姓 → 名」の並びのように、1列目で並べ、1列目が同じものを2列目で並べます。

そのため、上のインデックスは次のクエリに使えます：

- `WHERE customer_id = 42`
- `WHERE customer_id = 42 AND ordered_at >= '2026-10-01'`
- `WHERE customer_id = 42 ORDER BY ordered_at`

一方、次のクエリには使えません：

- `WHERE ordered_at >= '2026-10-01'`（1列目の条件がない）

電話帳で「名」だけから人を探せないのと同じです。

### 順番の決め方

列の順番は次の方針で決めます。

1. 等号（`=`）で絞り込む列を先に置く
2. 範囲（`<` `>` `BETWEEN`）で絞り込む列を後に置く
3. 並べ替えに使う列は、範囲の列と同じ位置か後ろに置く

範囲の条件を使った列より後ろの列は、絞り込みにほとんど使われません。

## インデックスの使えない書き方

インデックスがあっても、書き方によっては使われないことがあります。よくある例を挙げます：

- 列に関数を適用している：`WHERE LOWER(email) = 'a@example.com'`
- 列に計算をしている：`WHERE price * 1.1 > 1000`
- 型が一致していない：`WHERE phone = 09012345678`（文字列の列に数値）
- 前方一致ではない `LIKE`：`WHERE name LIKE '%田'`
- `OR` で別の列の条件をつないでいる：`WHERE a = 1 OR b = 2`
- 否定の条件：`WHERE status <> 'done'`
- `NULL` との比較を `=` で書いている：`WHERE deleted_at = NULL`
- 暗黙の型変換が起きる日付の比較
- 先頭がワイルドカードの正規表現
- インデックスの1列目を使わない複合インデックスの利用
- 統計情報が古く、全件走査の方が速いと誤判断される
- 取り出す行が多すぎて、全件走査の方が速い

多くは、条件の書き方を変えるか、関数を適用した結果に対するインデックス（式インデックス）を作ることで解決できます。

## インデックスのコスト

インデックスは検索を速くしますが、無料ではありません。

### 書き込みが遅くなる

行を追加・更新・削除するたびに、テーブルだけでなくすべてのインデックスも更新する必要があります。インデックスが10個あれば、1行の追加で11か所を書き換えることになります。

### 容量が増える

インデックスはテーブルとは別に保存されます。列の多い複合インデックスを多数作ると、テーブル本体より大きくなることもあります。

### 判断の基準

- 読み込みが多く、書き込みが少ないテーブルには積極的に作る
- 書き込みが非常に多いテーブルでは、本当に必要なものに絞る
- 使われていないインデックスは定期的に見つけて削除する

# 実行計画を読む

## EXPLAIN

データベースがクエリをどう実行するつもりかは、`EXPLAIN` で確認できます。これを**実行計画**と呼びます。

```sql
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE customer_id = 42
ORDER BY ordered_at DESC
LIMIT 20;
```

`ANALYZE` を付けると、実際にクエリを実行し、各工程にかかった時間と行数も表示します。

## 実行計画の例

インデックスがない場合の実行計画（PostgreSQL の例）：

```text
Limit  (cost=185431.20..185431.25 rows=20 width=64)
       (actual time=1523.4..1523.4 rows=20 loops=1)
  ->  Sort  (cost=185431.20..185433.70 rows=1000 width=64)
            (actual time=1523.4..1523.4 rows=20 loops=1)
        Sort Key: ordered_at DESC
        Sort Method: top-N heapsort  Memory: 27kB
        ->  Seq Scan on orders  (cost=0.00..185404.00 rows=1000 width=64)
                                (actual time=0.03..1522.9 rows=987 loops=1)
              Filter: (customer_id = 42)
              Rows Removed by Filter: 9999013
Planning Time: 0.1 ms
Execution Time: 1523.5 ms
```

`Seq Scan`（全件走査）で約1,000万行を読み、条件に合わない 9,999,013 行を捨てています。

## 改善後の実行計画

`(customer_id, ordered_at)` の複合インデックスを作ったあとの実行計画：

```text
Limit  (cost=0.56..80.12 rows=20 width=64)
       (actual time=0.04..0.12 rows=20 loops=1)
  ->  Index Scan Backward using idx_orders_customer_date on orders
        (cost=0.56..3978.30 rows=1000 width=64)
        (actual time=0.04..0.11 rows=20 loops=1)
        Index Cond: (customer_id = 42)
Planning Time: 0.2 ms
Execution Time: 0.2 ms
```

`Index Scan Backward` で、インデックスを後ろからたどって20行だけを読んでいます。並べ替え（`Sort`）も不要になりました。実行時間は 1523.5ms から 0.2ms になりました。

## 実行計画で見るべき項目

| 項目 | 意味 | 注意すべき状態 |
|---|---|---|
| `Seq Scan` | 全件走査 | 大きなテーブルで出ている |
| `Index Scan` | インデックスで探してテーブルを読む | — |
| `Index Only Scan` | インデックスだけで完結 | — |
| `Bitmap Heap Scan` | 複数の行をまとめて読む | — |
| `Sort` | 並べ替え | `Sort Method: external merge`（ディスクを使用） |
| `Hash Join` | ハッシュ表を使った結合 | `Batches` が 1 より大きい |
| `Nested Loop` | 入れ子のループによる結合 | 外側の行数が多い |
| `rows` | 見積もり行数 | 実際の行数と桁が違う |
| `actual time` | 実際の時間 | 特定の工程に集中している |
| `loops` | 繰り返し回数 | 大きい値 |
| `Rows Removed by Filter` | 条件で捨てた行数 | 読んだ行数に対して大きい |
| `Buffers: shared read` | ディスクから読んだページ数 | 大きい値 |
| `Planning Time` | 計画にかかった時間 | 実行時間より長い |
| `Execution Time` | 全体の実行時間 | — |

## 遅いクエリを直す手順

1. 遅いクエリを特定する（スロークエリログ、監視ツール）
2. `EXPLAIN ANALYZE` で実行計画を取る
3. 時間のかかっている工程を探す
4. 見積もり行数と実際の行数がずれていないか確認する
5. ずれていれば統計情報を更新する（`ANALYZE` 文）
6. 全件走査やディスクを使った並べ替えがあれば、インデックスを検討する
7. インデックスを作ったら、もう一度実行計画を取って効果を確かめる
8. 書き込み性能への影響も確認する

推測でインデックスを追加せず、必ず実行計画で効果を確かめましょう。

# まとめ

## 今日のまとめ

- 検索の速さは、ディスクから読むページ数でほぼ決まる
- B-tree インデックスは、数ページの読み込みで目的の行にたどり着ける
- 複合インデックスは列の順番が重要
- インデックスには書き込みと容量のコストがある
- `EXPLAIN ANALYZE` で実際の動きを確かめてから直す
