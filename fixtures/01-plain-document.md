# チーム開発のための Git 運用ガイド

チームで同じリポジトリを安全に扱うための、最低限のルールをまとめたガイドです。

## 目的

Git は自由度の高い道具です。自由度が高いぶん、人によって使い方がばらばらになりやすく、履歴が読みにくくなったり、他の人の作業を消してしまったりする事故が起きます。

このガイドの目的は次の3つです。

- 履歴を読めば「いつ・誰が・なぜ」変更したかが分かる状態を保つ
- 他の人の作業を壊さない
- 迷ったときに参照できる共通の手順を持つ

ルールは少なく保ち、守れないルールは見直します。

## ブランチ戦略

### main ブランチ

`main` は常にデプロイ可能な状態に保ちます。`main` に直接コミットしてはいけません。変更はすべてプルリクエストを通して取り込みます。

### 作業ブランチ

作業はすべて `main` から作成した作業ブランチで行います。1つのブランチでは1つの目的だけを扱い、目的が終わったらマージして削除します。

長く生きるブランチは避けてください。目安として、3日以上マージされないブランチは分割できないか検討します。

### 命名規則

| 接頭辞 | 用途 | 例 |
|---|---|---|
| `feature/` | 新機能 | `feature/login-form` |
| `fix/` | 不具合の修正 | `fix/null-user-name` |
| `docs/` | ドキュメントのみの変更 | `docs/setup-guide` |
| `refactor/` | 動作を変えない整理 | `refactor/split-service` |
| `chore/` | 依存関係の更新など | `chore/update-deps` |

## コミットのルール

コミットメッセージは次の形式で書きます：

```text
<種類>: <変更の要約（50文字以内）>

<なぜ変更したか。必要なら複数行で説明する>
```

種類には次のものを使います。

- `feat`：新機能
- `fix`：不具合の修正
- `docs`：ドキュメント
- `style`：書式の修正（動作に影響しない）
- `refactor`：リファクタリング
- `perf`：性能改善
- `test`：テストの追加・修正
- `chore`：ビルドや依存関係など

1つのコミットには1つの論理的な変更だけを含めます。「ついでに直した」変更は別のコミットに分けてください。

### 良い例と悪い例

```text
良い例：
fix: ユーザー名が空のときに一覧画面が落ちる問題を修正

API が name を省略する場合があり、表示時に null 参照が起きていた。
空文字として扱うように変更した。

悪い例：
修正
```

## プルリクエスト

### 作成前のチェック

- [ ] `main` の最新の変更を取り込んだ
- [ ] テストがすべて通る
- [ ] 不要なデバッグ出力を消した
- [ ] 説明欄に「何を・なぜ」変えたかを書いた
- [ ] 画面の変更があればスクリーンショットを添付した

### レビューの観点

レビューでは次の点を確認します：

1. 変更の目的が説明から理解できるか
2. 目的に対して変更が過不足ないか
3. 既存の動作を壊していないか
4. エラー時の動作が考えられているか
5. テストが変更内容を確かめているか
6. 名前から役割が分かるか
7. 重複したコードがないか
8. 性能に大きな影響がないか
9. 秘密情報が含まれていないか
10. ドキュメントの更新が必要ないか

レビューは24時間以内に返すことを目標にします。指摘には「必須」か「提案」かを明記してください。

### マージの方法

マージは原則として「Squash and merge」を使います。作業中の細かいコミットは1つにまとめられ、`main` の履歴が読みやすくなります。

> 大きな変更で、コミットごとの履歴を残す意味がある場合だけ「Rebase and merge」を使います。

## よくあるトラブル

### コンフリクトが起きた

慌てずに、`main` の最新を取り込んでから手元で解消します。

```bash
git fetch origin
git switch feature/login-form
git merge origin/main
# コンフリクトしたファイルを編集して解消する
git add <解消したファイル>
git commit
```

解消に自信がないときは、変更した人に相談してください。

### 間違えて main にコミットした

まだプッシュしていなければ、作業ブランチに移せます。

```bash
git switch -c feature/my-work   # 今の状態で新しいブランチを作る
git switch main
git reset --hard origin/main    # main をリモートの状態に戻す
```

プッシュしてしまった場合は、自分で直そうとせず、すぐにチームに連絡してください。

### 大きなファイルをコミットした

動画やビルド成果物などの大きなファイルは、一度コミットすると履歴に残り続けます。コミット前に `.gitignore` を確認してください。すでにプッシュした場合は、履歴の書き換えが必要になるため管理者に相談します。

## コマンド早見表

| やりたいこと | コマンド |
|---|---|
| 状態を確認する | `git status` |
| 差分を見る | `git diff` |
| ステージした差分を見る | `git diff --staged` |
| ブランチを作って移動する | `git switch -c <名前>` |
| ブランチを移動する | `git switch <名前>` |
| ブランチ一覧 | `git branch -a` |
| 変更をステージする | `git add <ファイル>` |
| コミットする | `git commit` |
| 直前のコミットを修正する | `git commit --amend` |
| リモートの変更を取得する | `git fetch` |
| 取得して取り込む | `git pull` |
| プッシュする | `git push` |
| 履歴を見る | `git log --oneline --graph` |
| 変更を一時退避する | `git stash` |
| 退避した変更を戻す | `git stash pop` |
| ファイルの変更を取り消す | `git restore <ファイル>` |
